# CLAUDE.md

## Working preferences

- **Clean code**: favor clear names, small focused functions, and no dead code. A call made only under a condition is an `if` statement, not an expression statement like `a and f()`, `a or f()` or `f() if a else g()`; `and`/`or` and conditional expressions are for computing values. `except` clauses name what they catch; never a bare `except:`. Keep it DRY: logic that appears more than once lives in one place. Follow the open/closed principle: design classes so new behavior (e.g. a new solving rule, cell behavior or puzzle shape) is added by adding code rather than by changing existing classes. While the program is still being built out, changing existing classes is fine when it keeps things simple; apply open/closed strictly once it is feature complete.
- **TDD**: write or update a failing test first, then make it pass, then refactor. Tests live in a `tests/` folder beside the code they test: the test for `game/cell.py` is `game/tests/cell_test.py`, for `game/rules/dead_end_rule.py` it is `game/rules/tests/dead_end_rule_test.py`, for `ui/terminal/display.py` it is `ui/terminal/tests/display_test.py`. Tests that cover both packages stay in the top-level `tests/`. Game tests use `game/tests/recording_ui.py` as their user interface.
- **Follow existing norms**: match the naming, structure, comment style, and idioms already used in this code base rather than introducing new conventions.
- **Method order**: place a called method as close as possible after the method that calls it, while keeping it in its own section (interface or private). Reading top to bottom, called methods then appear in the order they are used. When several callers share a method, place it after the first one. When adding or moving a method, check that its callees still follow it.
- **Sections**: group methods meant for a specific kind of caller under `# Interface required for <caller>` (e.g. `# Interface required for blocks`), and put all private methods last, under `# Private functions`. Test classes follow the same rule: helpers go under `# Private functions` after the tests. Large test classes also group their tests by category under plain `# <category>` comments (e.g. `# Undo and rewind`); add a new test to its category's section.
- **Constants first**: put class constants at the top of the class, right after the docstring and before any methods or other class state. If there is a docstring, put a blank line before the constant(s), otherwise no blank line. The exceptions are a constant built from a nested class, which Python requires to be defined first (e.g. `DisplayAttrs.ATTRS_PRIMARY` uses `FgBgAttr`), and a long table of data constants (e.g. `Display`'s drawing characters), which goes at the end of the class so it doesn't push the class's logic down a page.
- **Layers**: the game lives in `game/` and knows nothing about how it is shown: it talks to the player only through its user interface (the `UserInterface` port), and `tests/package_boundary_test.py` checks that nothing in `game/` imports from `ui` or `blessed`. Each way of showing it is a package in `ui/` (today `ui/terminal/`). The puzzle (the game: actions, modes, cursor) reaches cells only through its board. The board knows only its block layout and passes requests on to every block; only a block decides which of its own cells are in a given row or column, because in other puzzle types the blocks may not form a regular grid. Blocks give each cell its related cells (`related_cells`), and cells act on them, so new cross-cell behavior goes in `Cell` while blocks, the board and the puzzle stay unchanged. Nothing in the game draws: a cell reports each change (`cell_changed`) through its block and the board to the user interface, which decides how to show it. The one exception: the board can return a cell by position (`cell(row, col)`), for the cursor, the selected cell and restoring a saved game, since a sudoku's outer edge is always rectangular.
- **Puzzle layouts**: each layout is a `Board` subclass with a `NAME`, in its own file in `game/puzzles/`; `PuzzleCatalog` finds it automatically, and `Main` plays it as `Puzzle(board)`. Hooks a subclass must override (such as `_blocks()` and `_block_at()`) use a single leading underscore, because `__` names are mangled per class; all other private methods keep `__`.
- **Solving rules**: each rule is a `Rule` subclass in its own file in `game/rules/`, with its own test file in `game/rules/tests/` (sharing `game/rules/tests/rule_test_helper.py`), listed in `game/rules/order.py` (order matters: rules that stop solving come before rules that make moves). Rules only find moves (`find()` returns a `Move` or `None`) and never change the puzzle or the display; the solver and the puzzle make the move. Rules use only the puzzle's interface for the solver (`first_cell_where`); add to that interface when a new rule needs more.
- **Line endings**: working files use CRLF (Windows; `core.autocrlf=true` stores LF in git). Editing tools often write LF, so convert new or rewritten files and check with `git ls-files --eol` or by counting `\r` bytes, not with `grep $'\r$'` (Git Bash's grep hides carriage returns).
- **Sudoku solver**: keep in mind the rules of a basic 9x9 sudoku puzzle: the grid is divided into nine 3x3 boxes (three across and three down), and each row, each column, and each box must contain the digits 1–9 exactly once.
