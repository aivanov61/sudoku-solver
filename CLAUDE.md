# CLAUDE.md

## Working preferences

- **Clean code**: favor clear names, small focused functions, and no dead code. Keep it DRY: logic that appears more than once lives in one place. Follow the open/closed principle: design classes so new behavior (e.g. a new solving rule, cell behavior or puzzle shape) is added by adding code rather than by changing existing classes. While the program is still being built out, changing existing classes is fine when it keeps things simple; apply open/closed strictly once it is feature complete.
- **TDD**: write or update a failing test in `tests/` first, then make it pass, then refactor.
- **Follow existing norms**: match the naming, structure, comment style, and idioms already used in this code base rather than introducing new conventions.
- **Method order**: place a called method as close as possible after the method that calls it, while keeping it in its own section (interface or private). Reading top to bottom, called methods then appear in the order they are used. When several callers share a method, place it after the first one. When adding or moving a method, check that its callees still follow it.
- **Sections**: group methods meant for a specific kind of caller under `# Interface required for <caller>` (e.g. `# Interface required for blocks`), and put all private methods last, under `# Private functions`. Test classes follow the same rule: helpers go under `# Private functions` after the tests.
- **Constants first**: put class constants at the top of the class, right after the docstring and before any methods or other class state. If there is a docstring, put a blank line before the constant(s), otherwise no blank line. The exceptions are a constant built from a nested class, which Python requires to be defined first (e.g. `DisplayAttrs.ATTRS_PRIMARY` uses `FgBgAttr`), and a long table of data constants (e.g. `Display`'s drawing characters), which goes at the end of the class so it doesn't push the class's logic down a page.
- **Layers**: the puzzle knows only its block layout and passes requests on to every block; only a block decides which of its own cells are in a given row or column, because in other puzzle types the blocks may not form a regular grid. Blocks give each cell its related cells (`related_cells`), and cells act on them, so new cross-cell behavior goes in `Cell` while blocks and the puzzle stay unchanged. The one exception: the puzzle may reach a cell by position for cursor navigation and the selected cell, since a sudoku's outer edge is always rectangular.
- **Puzzle layouts**: each layout is a `Puzzle` subclass with a `NAME`, in its own file in `puzzles/`; `PuzzleCatalog` finds it automatically. Hooks a subclass must override (such as `_blocks()` and `_block_at()`) use a single leading underscore, because `__` names are mangled per class; all other private methods keep `__`.
- **Solving rules**: each rule is a `Rule` subclass in its own file in `rules/`, with its own test file in `tests/` (sharing `tests/rule_test_helper.py`), listed in `rules/order.py` (order matters: rules that stop solving come before rules that make moves). Rules use only the puzzle's interface for the solver (`first_cell_where`, `select`, `enter_solved_value`); add to that interface when a new rule needs more.
- **Line endings**: working files use CRLF (Windows; `core.autocrlf=true` stores LF in git). Editing tools often write LF, so convert new or rewritten files and check with `git ls-files --eol` or by counting `\r` bytes, not with `grep $'\r$'` (Git Bash's grep hides carriage returns).
- **Sudoku solver**: keep in mind the rules of a basic 9x9 sudoku puzzle: the grid is divided into nine 3x3 boxes (three across and three down), and each row, each column, and each box must contain the digits 1–9 exactly once.
